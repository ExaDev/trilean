# Contributing

`pnpm install` sets up git hooks automatically (`prepare: husky`). From then on:

- **Pre-commit** lints and auto-fixes staged files (`lint-staged`).
- **commit-msg** validates the message against [Conventional Commits](https://www.conventionalcommits.org/), enforced by commitlint. The allowed types, the release level each one triggers, and its changelog heading are defined once, in `release-workspace.config.ts`'s `commitTypes` (commitlint imports the same list, so a type can never pass one check and fail the other). As a rule: `feat` releases minor, a breaking-change footer/`!` releases major, everything else (`fix`, `refactor`, `docs`, `test`, `chore`, …) releases patch.
- **Pre-push** runs through turbo's cache the same matrix CI runs for the TypeScript side: lint, typecheck, `unit`, `integration`, `smoke` and `workers` for every package, plus the workspace root's lint and typecheck, so a push with nothing relevant changed since the last run is cheap. When the pushed commits touch `rust/`, `conformance/`, `scripts/`, the Rust workflows or `.husky/pre-push`, it also runs the Rust checks (`scripts/rust-checks.sh`). A push that touches none of those needs no Rust toolchain. The hook assumes git, a POSIX `sh`, `grep`, the Node and Python versions `.tool-versions` names and the pnpm version `package.json` names (`packageManager`); for the Rust checks it also needs [rustup](https://rustup.rs) and Python 3.9 or later (the scripts use only the standard library), and for those two it says what to install when they are missing. The integration project starts PostgreSQL through testcontainers, so it needs a container runtime: with Colima, set `DOCKER_HOST=unix://$HOME/.colima/default/docker.sock` and `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`, which turbo passes through to that task. CI also runs the `cargo-deny` allowlist check.

## Before opening a PR

`pnpm --dir packages/trilean run prepublishOnly` runs the same gate CI enforces for that package: lint, typecheck, `unit` + `integration` tests, build, `smoke` test, `publint`, and `attw --pack`. It does not run the `workers` project — run `pnpm test:workers` separately for any change touching `src/` (evaluator, schemas, resolvers), since that's what actually proves the isomorphism constraint below rather than merely asserting it.

## Constraints a change must preserve

- **Isomorphism.** `packages/trilean/src/**/*.ts` must never import a `node:*` module or reference `Buffer` — enforced by that package's own `eslint.config.ts` isomorphism guard and runtime-checked by the `workers` project running the evaluator inside a real Cloudflare Workers isolate (`packages/trilean/test/workers/`, `packages/trilean/wrangler.jsonc`). A change that needs a Node API belongs in a script or test file, or in `packages/trilean/cli/`, the one shipped place allowed Node APIs because it is the `trilean` command's own entry point (built to `dist-cli/`, kept out of `dist/` so the `./*` export cannot expose it); logic the command shares with the library stays in `src/`.
- **[Design principles](packages/trilean/README.md#design-principles).** No assumptions about consumer data, three evaluation outcomes never two, derived constructs built as compositions rather than new logic, one schema with mechanically derived artefacts. These hold across the whole design; an implementation change that would violate one needs the principle itself revisited first, not a quiet exception.
- **Generated files are never hand-edited.** `packages/trilean/schemas/trilean.schema.json` and everything under `packages/trilean/generated/` are written by `sh scripts/rust.sh xtask npm trilean` (the generator is `rust/xtask/src/generate.rs`) as part of `pnpm build`, from the Rust definition in `rust/crates/trilean-eval`, and are gitignored. If a shipped schema looks wrong, fix the Rust definition or the generator, not the output.

## Releases

Merging to `main` runs [`@exadev/semantic-release-workspace`](https://www.npmjs.com/package/@exadev/semantic-release-workspace) in CI, which runs semantic-release once per package. Each package is analysed against only the commits that touched its own directory, plus any extra source paths `release-workspace.config.ts` lists for it in `packageSources` (a package built from a Rust crate lists the crate and its binding crate, never `conformance/`), so its version tracks its own history, and a change to one package bumps another only through a dependency range, because the packages pin each other exactly and a dependent is re-released when its dependency is. A path is added to `packageSources` in the pull request that adds the crate it names, because the orchestrator refuses a path no commit has touched. A release publishes to npm, tags as `<name>@<version>`, and writes that package's own `CHANGELOG.md`.

A crate published to crates.io names the npm package it is built into in `[package.metadata.trilean-release] npm-package`, and has that package's version: the release's `prepare` step (`scripts/semantic-release-crate-versions.mjs`) writes the new version into the crate, the requirement its siblings give it and `Cargo.lock`, in the same release commit, and the `publish-crates` job then publishes every crate whose version crates.io does not hold, in dependency order, through crates.io trusted publishing. `python3 -I scripts/crate-versions.py check` fails a pull request whose crate versions disagree with their packages, and the `crates` job runs `cargo publish --dry-run` over every published crate. A crate's first release cannot go through trusted publishing, which is configured on a crate that exists: it is published once with an API token, and its trusted publisher (this repository, `ci.yml`) registered in its crates.io settings, before the job can publish it.

Never hand-bump a `package.json` or crate version or edit a `CHANGELOG.md` directly: each is overwritten by the next release. A commit's *scope* is free text and does not route it anywhere; what decides which package releases is which files the commit changed.
